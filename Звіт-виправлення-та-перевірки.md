# SOTA OS — короткий звіт про зміни

**Дата оновлення:** 26 вересня 2026 року

## Зміни

- Рішення явно зберігає мету та список зачеплених людей. Виконання звіряє рішення з базою й перевіряє згоду кожної іншої зачепленої особи на точні мету, контекст, дію та ресурс. Без відповідної згоди дія відхиляється.
- CLI показує умови згоди та записує її лише після точного підтвердження `НАДАЮ ЗГОДУ`; перегляд і відкликання доступні після автентифікації.
- Додано provider-neutral контракт початку/завершення автентифікації, прив’язку зовнішнього суб’єкта до Person у межах конкретної Sota unit та allowlist провайдерів для кожної unit.
- Додано локальний адаптер парольної фрази: PBKDF2-HMAC-SHA256, випадкова сіль, очищення тимчасових масивів, блокування після повторних невдалих спроб. Пароль не передається аргументом командного рядка.
- Legacy `IdentityProtocol.authenticate` тепер застарілий і завжди відмовляє; він більше не приймає наявність об’єкта credential за підтвердження особи.
- Описано шлях додавання зовнішніх адаптерів Google/OIDC, Дії, ЕЦП та інших у [ADR-009](docs/adr/ADR-009-provider-based-authentication.md). Самі зовнішні інтеграції ще не реалізовані.
- Додано Ed25519 event signing, actor-key lifecycle/audit, trusted peer admission, bearer credential authentication і authenticated `SyncEndpoint`.
- Додано typed P10 ports та voluntary self-exit service з обов’язковим portable export перед termination.
- Додано JDK 21 workflow у `.github/workflows/ci.yml` і ADR-003a/ADR-010.

## Перевірки

- Повний `./gradlew build --continue --console=plain` із Detekt, migration verification і 74 test cases: `BUILD SUCCESSFUL`, 31 actionable tasks.
- Focused security, sync, P10 і SQLite integration tests passed.
- CI wrapper integrity was fixed by regenerating the Gradle 8.10 wrapper; the canonical wrapper jar checksum is now `2db75c40782f5e8ba1fc278a5574bab070adccb2d21ca5a6e5ed840888448046`.
- P10 export-order regression fixed: `EXPORT_READY` is set only after `snapshot()` succeeds; a failed export cannot authorize termination.

## Межі поточної версії

`auth create` створює локальну Person/Identity; `auth enroll` прив’язує локальну автентифікацію до вже наявної Person за участі довіреного локального оператора. Це не є державною чи юридичною перевіркою особи. Список дозволених провайдерів задається під час складання конфігурації сервісу; керування ним через UI ще належить реалізувати.

## Наступні кроки

- Production peer credential provisioning governance and AC-18 source mapping.

- Реалізовано SQLite trusted peer registry, hashed bearer credentials, авторизовані
  enroll/rotate/revoke для peers і actor keys та атомарний append-only audit
  оператора, authority, мети й операції. Self-provisioning, прострочена/відкликана/
  contested authority, неправильний scope і заборона RightsConstraint відхиляються.
- Додано production policy з точними context, origin/relay, direction та entity
  assertion allowlists; обов'язковим Ed25519 підписом і перерахунком canonical

  EventSignatureAdmission → реальна P09 policy; inbound authentication і commit
  виконуються в одній транзакції, ротація/відкликання видимі без restart.

  98 тестів, 0 failures/errors/skipped; 24 нових перевірки production-P09.
